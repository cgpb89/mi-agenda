# Operations: Supabase, migrations, deploy, backups

## 1. Create the Supabase projects

Create **two** projects: one for the app (dev, then prod) and a separate one for automated tests. Tests truncate tables.

On each project:

1. **Database → Extensions:** `btree_gist` is installed by the migration itself (in the `extensions` schema). Nothing to do unless your plan restricts extensions.
2. **SQL editor:** run [`prisma/sql/roles.sql`](../prisma/sql/roles.sql) after replacing the placeholder password with a long random value. It creates the least-privilege runtime role `tempo_app`. It is safe to re-run.
3. **API settings:** keep the `app` schema **out** of "Exposed schemas". It is not exposed by default.

## 2. Connection strings

Supabase → Project Settings → Database → Connection string:

| Variable       | Use                         | Format                                                                                                           |
| -------------- | --------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL` | App runtime                 | **Transaction pooler**, port 6543, user `tempo_app.<project-ref>`, password from `roles.sql`, `?sslmode=require` |
| `DIRECT_URL`   | Migrations, seed, admin CLI | **Session pooler** (5432, user `postgres.<project-ref>`) or the direct host `db.<ref>.supabase.co:5432`          |

Why the runtime can use the transaction pooler:

- Prisma 7 connects through `@prisma/adapter-pg` without named prepared statements (no `statementNameGenerator`).
- The booking engine uses only **transaction-scoped** advisory locks and row locks.
- No session state is relied on.

Keep the pool small (`DATABASE_POOL_MAX`, default 5 per instance). On serverless platforms, multiply that by the expected concurrent instances and stay well under Supavisor's limit.

Migrations need a direct or session connection, because DDL and `migrate` bookkeeping do not run through the transaction pooler. That is why `DIRECT_URL` is read only by [`prisma.config.ts`](../prisma.config.ts) and the CLI scripts.

## 3. Migrations

- Migrations in [`prisma/migrations`](../prisma/migrations) are the **only** source of schema truth. Do not edit the schema in the Supabase dashboard.
- **`20261009000000_init`:** tables, enums, indexes and composite foreign keys. It was generated by Prisma.
- **`20261009000100_constraints_and_security`:** hand-written. It adds:
  - `btree_gist` and the GiST exclusion constraint;
  - CHECK constraints;
  - the appointment number sequence start;
  - partial indexes;
  - revocation of Supabase API roles and RLS enablement;
  - `app.tempo_apply_grants()`.
- **New migration:** edit `schema.prisma`, then run `npm run db:migrate:dev -- --name <change>` against a **dev** database. Review the SQL. If you added tables, append `SELECT app.tempo_apply_grants();`.
- **Deploy:** `npm run db:migrate:deploy` with `DIRECT_URL` set. Run it in CI or the release step **before** starting the new app version, and write migrations to be backward-compatible with the previous version (expand, then contract).
- `prisma db push` is not used.
- **Clean-build proof:** `npm run db:test:reset` rebuilds the test database from the migration history.

## 4. Deploying the app

Any Node 22+ host works, for example Vercel, Fly or a container.

1. Set the environment from `.env.example`. In production:
   - `NODE_ENV=production`
   - `APP_URL=https://…`
   - all three secrets
   - `RATE_LIMIT_STORE=postgres`
   - `TRUST_PROXY_HEADERS=true` only behind a proxy that overwrites forwarded headers
   - SMTP settings if you want emails sent
2. Run `npm ci && npm run build`, then `npm run db:migrate:deploy`, then `npm start`.
3. Check the health endpoint: `GET /api/health` returns `{ ok: true, db: "up" }`.
4. Create the first platform admin with `npm run admin:grant -- --email …`. Do **not** run the seed in production; it refuses to.

The app fails fast with a list of missing or invalid variable **names**, never values, if production configuration is incomplete.

## 5. Backups and restore

- **Backups:** Supabase takes daily backups. Enable **Point-in-Time Recovery** on paid plans for production. Before risky migrations, take a logical dump with the direct URL:

  ```bash
  pg_dump "$DIRECT_URL" --schema=app --format=custom --file=tempo-$(date +%F).dump
  ```

- **Restore to a new project:**
  1. Create the project.
  2. Run `roles.sql`.
  3. Run `pg_restore --no-owner --dbname "$DIRECT_URL" tempo-<date>.dump`.
  4. Run `SELECT app.tempo_apply_grants();`.
  5. Point `DATABASE_URL` and `DIRECT_URL` at the new project.
  6. Run `npm run db:migrate:deploy`, which is a no-op if up to date.
- **Rehearse restores** periodically on a scratch project.
- **Do not hard-delete data:** the runtime role cannot delete appointments, payments or audit rows. Corrections are made with status changes, voids and refunds.

## 6. Routine maintenance

- **Rate-limit table:** expired windows are swept opportunistically. If the table grows large, run `DELETE FROM app.rate_limit_buckets WHERE expires_at < now() - interval '1 day'`.
- **Sessions:** expired sessions are deleted when presented. A periodic `DELETE FROM app.sessions WHERE expires_at < now()` keeps the table small.
- **Dependencies:** keep them current. Re-run `npm audit`, then the full test suite, after upgrades.
